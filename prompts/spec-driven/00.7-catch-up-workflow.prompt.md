# Catch Up Workflow — resumir uma feature 00-11 sob uma revisão mais nova

Use `$spec-driven-engineering` para trazer um pacote de feature já iniciado sob uma revisão anterior do workflow (`manifest.json`'s `workflowVersion`) até o ponto em que ele satisfaz a revisão atual, sem refazer trabalho já válido e sem fabricar artefato ausente.

## Entradas

Se `{{FEATURE_SLUG}}` estiver ausente/literal, infira somente quando existir uma única feature ativa em `.specs/features/` ou registrada em `.specs/HANDOFF.md`; ambiguidade bloqueia. Não assuma que o pacote está desatualizado só porque esta etapa foi invocada — comprove com o diagnóstico abaixo.

### Diagnóstico (sempre executar primeiro, nunca pular)

1. Rode, contra o pacote existente:
   ```bash
   node skills/spec-driven-engineering/scripts/validate-feature-package.mjs .specs/features/{{FEATURE_SLUG}}
   node skills/spec-driven-engineering/scripts/validate-applicability-contract.mjs .specs/features/{{FEATURE_SLUG}}/applicability.md
   ```
   Trate a saída real desses comandos como a lista autoritativa de lacunas — nunca re-derive narrativamente o que está faltando.
2. Compare os campos presentes em `applicability.md` (se existir) contra `skills/spec-driven-engineering/assets/applicability.template.md` atual. Um pacote antigo tipicamente não tem `new-service-or-subsystem`, `material-operational-cost` e/ou `outcome-evidence` — isso é esperado, não é uma falha do trabalho já feito.
3. Verifique se `applicability.md` existe. Se não existir (feature iniciada antes de o Applicability Contract existir), você vai produzi-lo agora — mas com uma ressalva obrigatória: um `applicability.md` produzido depois de `07-execute` já ter começado é retroativo, não antecipatório. Ele ainda governa o que resta desta feature, mas nunca finja no `Racional` que foi produzido antes da implementação.
4. Verifique se `outcome-plan.md` é aplicável (via `applicability.md` resolvido no passo 3) e, se for, se já existe congelado. Se a implementação ou a observação em produção já começou, pré-registrar agora é tarde — não fabrique um `outcome-plan.md` retroativo fingindo que antecede a implementação. Registre esse caso explicitamente como blocker/risco aceito em vez de congelar uma pré-registração que já nasce comprometida (HARKing).
5. Recompute a exigência do backend representative gate pela regra atual (`deriveBackendRepresentativeGate` em `references/applicability-contract.md`). Uma feature que antes não precisava do gate pode agora precisar — os gatilhos `new-service-or-subsystem`, `material-operational-cost` e `complexity: large|complex` não existiam quando este pacote pode ter sido classificado. Se o gate agora é `required` e a implementação já está em `BUILD`/`BROWSER` ou além, isso é um blocker real: reporte, não ignore silenciosamente.

<allowed_outputs>
- `.specs/features/{{FEATURE_SLUG}}/applicability.md` (criação ou adição só dos campos novos — nunca reescrever/reclassificar campos já resolvidos sem uma mudança de fato descoberta)
- `.specs/features/{{FEATURE_SLUG}}/outcome-plan.md` (somente quando ainda genuinamente pré-implementação/pré-observação)
- `.specs/features/{{FEATURE_SLUG}}/09-tasks.md` (backfill mínimo — mapear trabalho já real em `T-` records; nunca inventar tarefa não executada)
- `.specs/HANDOFF.md` via `node skills/spec-driven-engineering/scripts/update-handoff.mjs` (nunca por escrita direta)
- `.specs/project/STATE.md` somente para decisão, blocker ou lição durável desta atualização
</allowed_outputs>

<forbidden_outputs>
- refazer ou reclassificar qualquer artefato 00-11 já válido só porque a revisão do workflow mudou
- fabricar `outcome-plan.md` retroativo quando implementação/observação já começou
- fabricar `09-tasks.md`/`10-adversarial-review.md`/`11-evidence.md` sem evidência real do trabalho já feito
- silenciar um backend representative gate que passou a ser `required` pela regra atual
- escrever `.specs/HANDOFF.md` diretamente, fora de `update-handoff.mjs`
</forbidden_outputs>

## Execução

Para cada lacuna real reportada pelo diagnóstico, feche-a com o mínimo necessário:

- **`applicability.md` ausente por completo**: produza-o a partir de `00-intent.md`/`01-spec.md`/`02-assumptions.md`/código já existente, seguindo `references/applicability-contract.md`. Marque no `Racional` que foi produzido retroativamente e a partir de qual estágio real do pacote.
- **`applicability.md` existe mas sem os campos novos**: adicione só os campos ausentes, infira pela mesma evidência das outras respostas já registradas, sem tocar nos campos já resolvidos. Registre a adição no `Changelog` do arquivo com data e motivo ("catch-up de workflow").
- **Backend representative gate passou a ser `required`**: se a implementação ainda não passou por `BUILD`, trate como qualquer outra feature — rode o gate normalmente antes de `BROAD BUILD`. Se já passou, pare e registre como `Bloqueios`: o gate precisa ser satisfeito antes de qualquer avanço adicional, mesmo que broad build já tenha começado sob a regra antiga.
- **`outcome-evidence: applicable` sem `outcome-plan.md`, ainda pré-implementação**: produza e congele `outcome-plan.md` agora, normalmente.
- **`outcome-evidence: applicable` sem `outcome-plan.md`, implementação/observação já em curso**: não congele retroativamente. Registre em `Bloqueios`/`STATE.md` que esta feature terá evidência de outcome de grade reduzida (o pré-registro não antecede a implementação) e siga.
- **`09-tasks.md` ausente**: crie o mínimo — uma ou mais `T-` records ligando `REQ/AC/SCN/AT` ao que já foi de fato implementado, sem inventar granularidade que não existiu.

<gate>
Catch-up `passed` somente quando `validate-feature-package.mjs` e `validate-applicability-contract.mjs` (e `validate-outcome-plan.mjs` quando aplicável) rodam limpos contra o pacote atualizado, e todo gate recém-obrigatório foi satisfeito ou está registrado como `Bloqueios` explícito — nunca reclassificado silenciosamente para `not-required` só para fechar o gate.
</gate>

Sobrescreva `.specs/HANDOFF.md` (via `update-handoff.mjs`) com o estágio real em que a feature deveria estar segundo o workflow atual — nunca "reiniciando" um estágio já concluído e válido.
