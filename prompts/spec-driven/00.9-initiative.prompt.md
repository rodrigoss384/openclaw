## Quando usar

Use este prompt apenas quando o pedido do usuário for maior que uma feature — um programa (ex.: "reconstruir todo o frontend", "migrar a plataforma de billing") que se decompõe em várias features 00–11 independentes, cada uma com seu próprio ciclo completo. Não crie uma initiative para uma feature única; isso é apenas overhead. O sinal claro é: você não conseguiria escrever um `01-spec.md` coerente e testável sem primeiro dividir o trabalho.

## Entradas

Em `{{PROJECT_ROOT}}`, carregue regras, `.specs/HANDOFF.md`, `.specs/project/PROJECT.md`/`STATE.md` e a solicitação atual do usuário.

<allowed_outputs>
- `.specs/initiatives/{{INITIATIVE_SLUG}}/initiative.md`
- `.specs/HANDOFF.md`
- `.specs/project/STATE.md` somente para decisão, blocker, lição ou ideia adiada durável
</allowed_outputs>

<forbidden_outputs>
- qualquer artefato 00–11 de feature individual (isso pertence ao ciclo normal de cada feature)
- código, teste ou configuração
- decisão técnica de uma feature específica que deveria ser resolvida no `01-intent`/`02-spec-assumptions` daquela feature
</forbidden_outputs>

## Execução

Produza `.specs/initiatives/{{INITIATIVE_SLUG}}/initiative.md` cobrindo:

- **Target architecture**: a arquitetura de destino em alto nível (não substitui `07-design.md`/`03-frontend-architecture.md` de nenhuma feature — apenas declara a direção que todas devem seguir).
- **Technology decisions**: decisões de stack válidas para todo o programa (ex.: adotar `replacement` como modo do `frontend-product-builder`, TanStack Router como baseline).
- **Migration/cutover strategy**: big-bang vs. incremental, ordem de corte, estratégia de rollback ou containment.
- **Design-system foundation**: se o programa exige um design system novo/consolidado antes das features de tela, declare-o como pré-requisito.
- **Quality gates**: quais gates do ciclo 00–11 se aplicam a toda feature do programa (normalmente todos — a initiative não cria exceção aos gates canônicos).
- **Rollout plan**: sequência de features com dependências entre elas. A tabela usa as colunas `Feature slug` (um slug entre crases por linha) e `Depende de` (slugs de features do mesmo plano entre crases, ou `—`). `workflow-entry.mjs begin` lê essa tabela: recusa iniciar uma feature do plano enquanto a initiative não estiver `ready` ou enquanto qualquer dependência declarada não tiver `evidence-release` completo em `stage-state.json`, e `next` reporta `blocked-by-initiative`. Tokens entre crases que não são slugs do plano (IDs `AD-`, `D-`, `C-`) não contam como dependência.
- **Lista de features**: cada feature do programa recebe seu próprio `FEATURE_SLUG` e roda o ciclo 00–11 completo de forma independente, referenciando esta initiative em `00-intent.md`. A initiative nunca substitui o `01-spec.md`/`applicability.md` de uma feature individual.

Não decomponha a initiative em tasks (`09-tasks.md` pertence a cada feature, não à initiative). Não avance nenhuma feature do rollout plan além do que a initiative já autorizou como pronto para começar.

<gate>
Initiative `ready` quando target architecture, technology decisions, cutover strategy e a lista inicial de features estão declarados e coerentes com `rules.md`. Decisão de arquitetura ou stack ainda pendente mantém `blocked` — nenhuma feature do rollout plan pode iniciar `01-intent` antes disso; `workflow-entry.mjs begin` bloqueia mecanicamente enquanto `## Status` não declarar `ready`.
</gate>

Sobrescreva `.specs/HANDOFF.md` com o estado da initiative e qual feature do rollout plan deve iniciar `01-intent` a seguir.
